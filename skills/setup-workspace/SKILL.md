# Подключение к проекту

Проверь оснастку для указанной роли в одном проекте. Принимай путь или текущий репозиторий, роль и harness. Выведи последние два из запроса, активной среды или профиля, если это однозначно. Если выбор меняет нужные инструменты или права, уточни его. Для знакомства с продуктом и разбора Issue есть отдельные этапы.

## Найди действующие правила

1. Установи корень репозитория и прочитай применимые инструкции, например `AGENTS.md`. Открой профиль по ссылке из этих инструкций. При отсутствии ссылки проверь `docs/agents/project-workflow.md` и существующую документацию по разработке.
2. Для проверки используй версию skillset и правила из профиля, источники задач, команды проекта из CI или документации и место хранения доказательств. При расхождении между источниками покажи его владельцу профиля.
3. Если профиля нет или он неполный, собери факты из репозитория и предложи черновик только для недостающих сведений. Укажи владельца, поддерживаемые роли и harness, версию skillset, источники контекста и задач, команды и обязательные гейты, доступ по ролям, доставку, приёмку и хранение доказательств. Пометь неизвестное. Общий профиль и ссылку из инструкций проекта записывай по согласованию с техническим владельцем.

## Проверь рабочее место

Проверь то, что понадобится для следующего действия в указанной роли.

| Область | Что подтвердить |
| --- | --- |
| Harness и навыки | Видны нужные навыки из требуемого источника. Версию или ревизию записывай, если она доступна. При совпадении имён установи, какую копию выбирает harness, либо отметь это как непроверенное. |
| Контекст и задачи | Открываются нужные инструкции, спецификации и источник Issue. Локальный Markdown подходит, если так определено проектом. |
| Инструменты и среда | Доступны программы и версии для работы роли, есть доступ к нужному локальному контуру или стенду. Проверяй безопасными командами вроде проверки версии или штатной диагностики. |
| Проверки и доказательства | Понятны команды и условия запуска обязательных гейтов, а также расположение отчётов. Для ревью установи, позволяет ли harness создать два независимых контекста, если это требуется проекту. |

Разработчику обычно нужны исходники, задачи и локальные проверки. Тестировщику — критерии, тестовые данные, контур и отчёты. Принимающему или проверяющему — фиксированный diff, точный источник требований, стандарты и доказательства. Профиль проекта определяет конкретные требования.

Наличие CLI, файла конфигурации или переменной окружения доказывает только их наличие. Отдельно отметь, удалось ли проверить фактическую загрузку навыка, разрешение на действие или доступ к ресурсу. Для проверки доступа используй штатную диагностику по месту и выводи результат без значений секретов.

## Предложи и примени настройки

Начни с диагностики. Подготовь конкретные изменения с указанием места и причины. Используй проектные способы настройки инструментов и менеджер канонического skillset с ревизией из профиля. Локальную оснастку меняй по согласию специалиста, общие файлы проекта — по согласию владельца. Если точное действие уже разрешено, примени его сразу. После изменений повтори только относящиеся к ним проверки.

Заверши настройку на найденном блокере с конкретным следующим действием. Подключение заканчивается отчётом о готовности; реализация Issue, прогоны CI, публикация артефактов и Git-операции доставки идут отдельными шагами.

## Отчёт

Дай короткую таблицу `Что проверено | Результат | Основание или следующее действие`. Используй статусы **Готово**, **Требует настройки**, **Заблокировано**, **Не проверено**. Для каждого пробела укажи ответственного, если известен. Укажи отдельно, готова ли оснастка для ближайшего действия в выбранной роли, и на что опирается этот вывод. Список создай в чате, если проект или пользователь не указал место для сохранения.
